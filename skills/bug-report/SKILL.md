\# 버그 기록



\## 1. 정보 모으기

직접 확인할 수 있는 것은 먼저 확인하고, 모르는 것만 한 번에 묶어서 묻는다.

\- 직접 확인할 것 : 시간(date), 작업자(GitHub 사용자명), 브랜치와 커밋, 최근 에러 로그

\- 사용자한테 물을 것 : 무엇을 하다가 발생했는지, 기대한 결과



\## 2. 작성 양식

버그 작성은 2단계로 나눠서 진행한다(이슈 발견 시 등록, 이슈 조치 시 해결 기록).



1\) 버그 발견 등록(이슈 생성)

\- 제목 형식 : \[bug] 짧은 요약

\- 내용 : 에러 시간, 작업자, 환경(브랜치, 커밋, 기기), 에러 상황, 재현 절차, 기대 결과와 실제 결과, 에러 메시지

\- 참고사항 : 스크린샷, 관련 기능 ID가 있으면 추가

\- 등록 전에 같은 이슈가 있었는지 먼저 검색한다.

\- 이슈 발행 전에 사용자에게 해당 내용으로 작성해도 되는지 확인받고 작성한다.



2\) 해결했을 때 (같은 이슈에 댓글)

\- 이슈 번호를 모르면 열린 bug 이슈 목록을 보여주고 사용자에게 고르게 한다.

\- 작성 내용 : 원인(확인된 것과 추정하는 것을 구분해서 작성), 수정 방안, 수정 후 결과, 관련 PR

\- 댓글을 달고 이슈를 닫기 전에 사용자에게 확인받는다.



\## 3. 저장 위치

GitHub issue에 bug 라벨을 붙여 남긴다(gh CLI 사용).

bug 라벨이 저장소에 없으면 사용자에게 만들지 묻는다.



\## 하지 말 것

\- 로그 전체를 붙이지 않고 관련 줄만 붙인다.

\- API 키, 비밀번호, 실명 등 민감한 정보는 붙이지 않는다.

\- 현재 상황을 확인해 보지 않고 마음대로 추측하여 개선 방안을 내지 않는다.

\- 사용자 확인 없이 이슈를 등록하거나 닫지 않는다.

\- 커밋 메시지에 Closes/Fixes #번호를 넣지 않는다(push 시 이슈가 자동으로 닫힘). 이슈 연결은 Refs #번호로 한다.
